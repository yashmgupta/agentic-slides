# Roadmap and solo-creator execution plan

## Current status

The research snapshot, architecture, prompts, local renderer, tests, and three example deck pairs exist in this working directory. This is not a public GitHub release. The product name is provisional and collides with existing public project/package names. No PDF renderer, AI provider integration, or external comparison benchmark is included.

## Milestones

Estimates separate automated agent work (which can run while the creator is away) from the creator's ~30 minutes/day for review and decisions. At six work sessions per week, 30 minutes/day is about three focused hours weekly.

| Milestone | Status / work | Automated agent time | Creator time |
|---|---|---:|---:|
| 1. Research completed | Complete: 30 candidates catalogued; ten documented in depth; evidence boundaries and licenses recorded | ~1–2 hours of research execution | ~2–3 hours to review choices and citations |
| 2. Core architecture validated | Complete as a documented MVP design and passing structural tests; HTML screenshot generated locally | ~30–60 minutes for tests/build | ~1–2 hours to inspect format tradeoffs |
| 3. Working MVP | Complete locally: JSON validator, QA, deterministic theme/layouts, PPTX and HTML exporters | ~1–2 hours implementation/testing | ~1 hour to review errors and priorities |
| 4. Tested presentation outputs | Files generated for 10-, 8-, and 6-slide examples; package/structure tests pass. Manual cross-viewer visual inspection remains a release task | ~30–60 minutes for reruns and report | ~1.5–2.5 hours to inspect slides and adjust examples |
| 5. GitHub release | Pending approval: choose cleared name, inspect source/asset licenses, update clone links, review package, then create repo/release | ~30–60 minutes to prepare | ~1–2 hours; publication must be explicitly approved |
| 6. First Medium article | Pending creator review and actual image capture; use an educational tutorial and clearly label synthetic data | ~30–60 minutes for draft outline | ~2–3 hours writing/editing, plus publication decision |
| 7. Improvements and articles | Add only after feedback: chart types, citations/provenance, accessibility, optional models, or tested PDF | ~1–3 hours per focused implementation | ~30 minutes/day for prioritization and acceptance |

These are planning estimates, not measured durations. Work already completed may be done by an agent faster than the remaining human review/publication effort.

## Practical next 30-minute sessions

1. Inspect the 10-slide HTML deck in a browser; check headline, spacing, and navigation.
2. Open all three PPTX files in an Office-compatible viewer and inspect every slide; focus on chart labels, speaker notes, and font substitution.
3. Fix any concrete clipping/contrast defects and rerun `npm test`.
4. Decide whether to rebrand. Do not publish under the current working title until a proper name/trademark/package check is done.
5. Review licenses and source links; ensure no screenshots or third-party assets were added without rights.
6. Draft the first tutorial from the working prompt and a clearly labeled sample; personally verify every result and claim.
7. Obtain explicit approval before repository creation, public release, or paid model usage.

## $0 guardrails

- No paid LLM or image-generation API is required for the MVP.
- No hosting, database, or container service is needed.
- Local rendering and browser/PPTX inspection are enough for the first iteration.
- Optional PDF or model integration should be deferred until free-tool quality and costs are tested.

## Release checklist

- [ ] Choose a non-conflicting name and verify relevant GitHub/npm/trademark usage.
- [ ] Inspect all generated PPTX/HTML outputs in target viewers.
- [ ] Confirm charts match the JSON, notes are present, and no content is presented as real evidence when synthetic.
- [ ] Review all research links, date stamps, licenses, and third-party attribution.
- [ ] Confirm README screenshots are generated by this code and have no sensitive content.
- [ ] Run `npm ci`, `npm test`, and sample generation from a clean checkout.
- [ ] Replace illustrative repository clone URL with actual approved URL.
- [ ] Review license ownership and contributor details.
- [ ] Obtain explicit user approval before creating or publishing a GitHub repository.
